feat(quant): 2-bit base + LoRA training, verified against the predicted loss

quant_lora.py already had the right shape -- frozen quantised base, fp32 LoRA pair,
dequantisation recomputed in backward instead of saving fp32 weights, and the
dequantised weight cached across steps because the base never changes. That last
property also settles a question I had been working towards: making the quantiser
differentiable is unnecessary, because gradients never reach the base weights. The
only thing missing was a 2-bit option, so this adds 'nf2' as a branch rather than
reimplementing the machinery.

End to end, on a 512-sample validation slice:

    fp32 base                              5.5038   (sanity, matches earlier runs)
    2-bit nf, only nn.Linear replaced      5.5538   predicted 5.5538, diff +0.0000
    after 60 LoRA steps, lr 1e-4           batch loss 5.70 -> 4.54

Because lora_B starts at zero and the base is frozen, the loss before training must
equal the quantised base's loss -- which is why the 5.5538 match is a real check and
not a coincidence. After 60 steps the training loss is below the fp32 model's
validation loss, so the adapter is genuinely learning.

Memory: 63 layers occupy 8.92 MB (7.48 MB packed + 1.87 MB absmax) against 114.16 MB
of fp32 weights -- 12.8x, matching the format arithmetic. Trainable parameters are
1.309M of 30.5M, i.e. 4.29%.

Two mistakes in the first run of this test are worth recording because neither was a
code fault. The loss was compared against the with-embeddings expectation while
quant_lora only replaces nn.Linear, and a training loss over batches of four was
compared against a validation loss. Both are the same scope error that recurred all
day: a criterion that does not measure what it is used to conclude.
