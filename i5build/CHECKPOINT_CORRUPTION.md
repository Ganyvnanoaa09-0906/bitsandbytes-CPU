# Qwen-Image-2.1 checkpoint: 本地副本损坏

## 结论

本地 `D:\work\qwen_env\Qwen-Image-2.1` 的 transformer 与 text_encoder 分片**内容损坏**:
约 2/3 的 1 MB 窗口**完全是零**,而远端同一区间是密度正常的权重数据。

**远端原件是好的。** VAE 和 text_encoder-1 是好的。

## 判据链(每条都是独立测量)

### 1. 全零张量按张量统计

全零的都是 100.66 MB 的 MLP 投影(`gate_proj`/`up_proj`/`down_proj`/`img_mlp.*`)和若干
attention 投影(如 `to_q`)。`norm_q`/`norm_k` 也是全零 —— 但**它们在远端原件里就是零**
(架构如此),不属于损坏。

### 2. 文件结构完好,所以不是截断

`safetensors` 头部声明的数据长度与文件实际长度**逐字节一致(差值 0)**:

| 文件 | 文件大小 | 头部声明 | 差 |
|---|---|---|---|
| transformer-1 | 9,968,332,504 | 9,968,307,712 | +0 |
| transformer-2 | 4,261,951,904 | 4,261,941,760 | +0 |
| text_encoder 各分片 | — | — | +0 |
| vae | 1,350,989,512 | 1,350,961,616 | +0 |

**长度对的文件仍然可以是零填充的** —— 这正是本项目早先那次"分段下载器假成功"的同一形态。

### 3. 三次独立读取同一结论

对 `transformer_blocks.0.attn.to_q.weight`(16,777,216 个元素)三种方式读取全部得到全零:

- `safetensors.load_file`
- `safe_open().get_slice()`
- **手写的裸字节解析**(读头部 → 定位 `data_offsets` → 按 dtype 直接 `np.frombuffer`)

所以不是某个库的读法问题。

### 4. 与远端逐字节对比(决定性)

对每个张量取其中间 4 KB 切片,同时向 `hf-mirror.com` 与 `modelscope.cn` 发起 Range 请求:

| 张量 | 本地 | hf | ms | 判定 |
|---|---|---|---|---|
| `transformer_blocks.3.img_mlp.proj.weight` | 全零 | nonzero | nonzero | 本地错 |
| `transformer_blocks.0.attn.to_q.weight` | 全零 | nonzero | nonzero | 本地错 |
| `layers.18.mlp.up_proj.weight` | 全零 | nonzero | nonzero | 本地错 |
| **`img_in.weight`(对照)** | 非零 | **SAME** | **SAME** | 比较方法有效 |
| **`txt_in.text_norm.weight`(对照)** | 非零 | **SAME** | **SAME** | 同上 |
| **`decoder.conv_in.weight`(对照)** | 非零 | **SAME** | **SAME** | 同上 |

**对照全 SAME 是关键**:它同时证明了比较方法可靠、网络路径可靠、以及远端原件正确。
没有这三个对照,上面三条"本地错"就只是"两边不一致",无法定位是哪一边错。

### 5. 零区的分布是双峰的

对 transformer-1 按 1 MB 窗口统计零字节密度:

```
0%           :    0 窗口 ( 0.0%)
0-10%        : 2724 窗口 (28.7%)
10-50%       :    3
50-90%       :    3
90-99%       :    2
99-100%      :    1
100%(全零)   : 6774 窗口 (71.3%)

最大连续全零段: 2229 MB @ offset 154,140,672
```

真实 bf16 权重不可能有 0% 的零字节,所以"0-10%"那 2724 个窗口**也不是完好数据**。

### 6. 指纹:完好区逐字节一致,零区是纯零

24 点均匀采样,每点取 1 MB 与远端同区间比对:

```
                 本地                     远端
24,792         zeros 0.1%  256/256  SAME      ← 完好
154,165,464    zeros 100%  1/256    DIFFERS
433,383,884    zeros 100%  1/256    DIFFERS
866,742,977    zeros 100%  1/256    DIFFERS
1,300,102,070  zeros 100%  1/256    DIFFERS

agree 8, differ 16, error 0 / 24
```

完好窗口**逐字节等于远端** ⇒ 不存在任何"变换",就是**具体的 1 MB 块被写成了零**。

两个一致的特征指向写入路径而非网络:

- **每个损坏文件的首个坏窗口都在 offset 201,326,592(192 MB)**,五个文件各不相同、
  大小不同、下载时间不同,却对齐到同一偏移
- **两个完好文件(text_encoder-1、vae)都是一次跑完全程、中途没有中断的**

机制尚未确认,本文件不对机制下结论。


## 两个被自己否证的错误机制(留作记录)

这一轮我先后提出了两个机制解释,**都被后续测量否证**,而结论不依赖它们:

1. **"行分块复用第 0 行权重"** —— 读 `gemv2_proto.c` 时推断的,但独立检验显示块内各行
   输出**并不相同**(差 144.8% RMS),该假设要求它们相同。
2. **"稀疏空洞"** —— 推断分段写入 seek 跳过了未写区域。实测零 run 是**单字节**的
   (2236 个),且紧邻字节与远端一致,与"大段空洞"矛盾。

教训:**在机制未被测量确认前不要把它写进结论。** 本次修复只需知道"本地内容错、远端对",
不需要知道写入路径为何产生零。

## 处置

1. 已删除 5 个损坏源文件(24.93 GB)与由它们派生的 4bit checkpoint(7.64 GB)
2. 用 `hf_safe_fetch.py` 重新完整下载(**不复用任何已有字节**)
3. 新下载器:**每写一个窗口就从文件回读比对**;只有全部窗口验证通过才把 `.part`
   改名为正式文件;不做任何基于长度的续传;最后再对全部窗口做一遍完整验证
4. 保留两个已验证完好的文件(text_encoder-1 4.65 GB、vae 1.26 GB)

**尺寸检查不足以判定完整性** —— 这已经是本项目第三次遇到"长度完全正确、内容是零"
(前两次:分段下载器对小文件假成功、`copy_` 写 meta 张量静默无效)。判定完整性必须
比对内容,不能比对长度。
